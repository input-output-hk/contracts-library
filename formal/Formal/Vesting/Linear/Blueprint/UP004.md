# UP-004 standalone rejected transactions candidate

This candidate asks for one model-valid Claim transaction and one model-valid
Cancel transaction that the fixed linear-vesting program rejects within
1,000,000 CEK steps. Rejection means an error or a non-unit halt. Exhausting the
step bound does not establish rejection; the bound is not a ledger CPU or memory
budget.

Irfan introduced these checks and transaction shapes in
[PR #44](https://github.com/no-witness-labs/contracts-library/pull/44) at `99a5734`.
[PR #56](https://github.com/no-witness-labs/contracts-library/pull/56) extracted them
for [issue #25](https://github.com/no-witness-labs/contracts-library/issues/25).
[SomeRejected.lean](SomeRejected.lean) retains both existential statements unchanged;
[Tx.lean](Tx.lean) defines their fixed models.

[Types.lean](Types.lean) embeds the exact 1,404-byte compiled program from the
tracked `onchain/plutus.json`, built with Aiken `v1.1.22+39d6b04`. Its recorded
script hash is `95da21788eb1f59f51aad9669eb8c8b7081ab618c1f29b871925894a`.
The embedded bytes are Lean source, so these checks need no external CBOR file or
Aiken rebuild.

## Run the candidate

Use Lean 4.24.0, Z3 4.15.2, and the dependency revisions committed in
[`lake-manifest.json`](../../../../lake-manifest.json):

| Dependency | Revision |
| --- | --- |
| Blaster | `402f6d22c1fc42e6e26255faac77e15b2450e4ab` |
| PlutusCore | `4ef48606303c45225d3ed2e2a87fc50280a763b7` |
| CardanoLedgerApi | `577e3eb03b5be09354cfdb1c0d0c12e9e16541a0` |

From `formal/`, build the supporting modules, then run the two declarations with
a five-minute wall clock limit. `Elab.async false` checks declarations sequentially;
the Lean process retains four workers.

```sh
lake build Formal.Vesting.Linear.Blueprint.Types Formal.Vesting.Linear.Blueprint.Tx
timeout --kill-after=5s 300s lake env lean --threads=4 --json Formal/Vesting/Linear/Blueprint/SomeRejected.lean
```

Expected: two `Valid` results, for `someRejected_claim` and `someRejected_cancel`,
and exit 0. A timeout leaves the candidate unresolved. Successful Blaster results
retain its SMT trust through `blasterProven` and the existing dependency trust
assumptions.

## Run the negative control

[AcceptingControl.lean](../../../Properties/Universal/UP004/Tests/Standalone/AcceptingControl.lean) independently
states the same two existential claims using a synthetic UPLC lambda that ignores
its context and returns unit. It retains the Claim/Cancel constructors, model
validity predicate, genuine-rejection predicate, and 1,000,000-step bound. Only the
checked program changes. This synthetic program is neither an Aiken build nor a
deployed validator.

```sh
timeout --kill-after=5s 300s lake env lean --threads=4 --json Formal/Properties/Universal/UP004/Tests/Standalone/AcceptingControl.lean
```

Expected: two `Falsified` results, for `someRejected_claim_control` and
`someRejected_cancel_control`, and a nonzero Lean exit. This deliberate failure
shows that the rejection-existence checks fail for a program that always accepts
these contexts. A timeout, import failure, compilation error, or solver error does
not count as a successful control. The control is outside the `Formal` library
and does not import the original proof module.

## Scope and checkpoint 2

Claim uses two inputs and two outputs; Cancel uses two inputs and one output.
Both models use one vested asset under the literal policy `policyA`, key
credentials for the beneficiary and locker, and one signer. The validity range has
a lower bound and no upper bound. The constructors use no reference inputs,
withdrawals, minting, or certificates. Their leaves remain symbolic.

A `Valid` result establishes an existential rejection within each supplied model.
It does not establish that every invalid transaction rejects, that authorization
is correct, or that the witnessed context is reachable on the ledger. Model
validity does not impose the full ledger rules, including key-hash lengths. Other
transaction structures and validators are outside this candidate's scope.

The owner deferred the 1 ADA minimum for every output and a printed rejected
example to checkpoint 2 under
[issue #25](https://github.com/no-witness-labs/contracts-library/issues/25).
These requirements are absent from the retained candidate.

Broader model coverage and native model-bank adoption belong to
[issue #89](https://github.com/no-witness-labs/contracts-library/issues/89).

Integration with `plutus-upv` and the native property bank belongs to
[issue #96](https://github.com/no-witness-labs/contracts-library/issues/96).

Checkpoint 1 covers the standalone Lean candidate. These broader issues remain
open for checkpoint 2.
