# UP-014: bounded continuation-datum example

Current helper references use `Formal.Support`. Statements below about unchanged
fully qualified names describe the earlier extraction checkpoint; the later
support-folder cleanup updates those names while preserving definition bodies.


This candidate checks the pinned linear-vesting validator with the original
Claim and Cancel transaction models in [Tx.lean](Tx.lean).
[ContinuationOtherDatum.lean](ContinuationOtherDatum.lean) preserves the four
propositions extracted from Irfan's work in PR #44 and recorded in PR #61 at
`df712cb869e1cf67537ef0c0f7b1241aaae5fa65`. They are `Prop` definitions so that the
module builds even when an expected applicability result is Falsified. The
standalone files in [tests/UP014](../../../../tests/UP014) invoke Blaster separately
from the `Formal` library.

## Claim and applicability

The mutation replaces the first continuation's inline datum with exactly:

```text
Constr 0 [credential1, credential2, List [], Int start, Int end, Int recovery]
```

The two credentials and three integers are symbolic. The vesting list is always
empty. The original Claim datum has one vested asset, so this replacement removes
that entry. The mutation does not cover every typed `VestingDatum`, nonempty replacement
vesting lists, or semantically valid alternative schedules.

The primary statement keeps all five original guards: model-valid original
context, accepted original context, explicit rejection after redirecting all
continuations, a different replacement datum, and model-valid mutated context.
It then requires explicit rejection of the mutation. Acceptance and rejection
use 1,000,000 CEK steps. Rejection means an error or non-unit halt within that
bound; exhaustion does not count as rejection. The bound is not a ledger CPU or
memory budget.

The applicability statement asks for a witness satisfying those same guards.
Claim has two inputs, two outputs, one signer, and one vested asset under literal
`policyA`. Its first output returns to the script. Cancel has two inputs and one
key-address payout, with no continuing output. Redirecting Cancel therefore
leaves it unchanged: original acceptance and redirection rejection cannot both
hold. Its passing primary statement provides no applicable coverage.

| Original statement | Retained observation | Interpretation |
| --- | --- | --- |
| Claim rejection | Valid | Empty-list replacement is rejected under the guards. |
| Claim applicability | Valid | The guards admit an accepted model-valid Claim. |
| Cancel rejection | Valid | Vacuous because the continuation-reliance guard cannot hold. |
| Cancel applicability | Falsified | No applicable Cancel coverage in this model. |

The retained checkpoint run reported these four outcomes in 115.132 seconds.
The negative Claim control reported Falsified for the property and Valid for
applicability in 29.795 seconds. Both commands exited 1 because the expected false
statement failed. A timeout or unrelated compiler error would not satisfy those
expectations.

These are retained solver observations from before the shared-helper relocation.
The nineteen helper bodies and their fully qualified names were preserved in
[CandidateHelpers.lean](../../../Support/CandidateHelpers.lean). A later pure
module build passed after the import change; it was not a solver rerun and does
not establish final-head proof execution. Final combined-source validation remains
a delivery gate. Compiling the `Prop` definitions alone proves none of the four
statements.

[Artifact.lean](../../../../tests/UP014/Artifact.lean) compares the tracked vesting

must reject. These six observations are concrete execution checks, not universal
proofs.

## Reproduce the standalone checks

Use Lean `v4.24.0` and the revisions already pinned in `lake-manifest.json`:
Blaster `402f6d22c1fc42e6e26255faac77e15b2450e4ab`, PlutusCore
`4ef48606303c45225d3ed2e2a87fc50280a763b7`, and CardanoLedgerApi
`577e3eb03b5be09354cfdb1c0d0c12e9e16541a0`. Blaster needs Z3 `4.15.2` on `PATH`.
The normal standalone commands use tracked artifacts and do not require Aiken.

Run these commands from `formal/`. Compile the support module explicitly
because it lives outside the default `Formal` library. These preparation and
concrete commands do not invoke Blaster.

```sh
timeout --kill-after=5s 60s lake build Formal.Vesting.Linear.Blueprint.ContinuationOtherDatum
mkdir -p .lake/build/lib/lean/tests/UP014
timeout --kill-after=5s 60s lake env lean --threads=4 -o .lake/build/lib/lean/tests/UP014/Support.olean tests/UP014/Support.lean
timeout --kill-after=5s 60s lake env lean --threads=4 tests/UP014/Artifact.lean
timeout --kill-after=5s 60s lake env lean --threads=4 tests/UP014/Concrete.lean
```

Run the solver checks separately with four Lean workers and a five-minute
wall-clock limit per command. The wall-clock limit is separate from the CEK bound.

```sh
timeout --kill-after=5s 300s lake env lean --threads=4 --json tests/UP014/Checks.lean
timeout --kill-after=5s 300s lake env lean --threads=4 --json tests/UP014/NegativeControl.lean
```

`Checks.lean` must report three Valid results followed by one Falsified result.
`NegativeControl.lean` must report one Falsified result followed by one Valid
result. Both commands intentionally return a nonzero status for the false
statements. Inspect every result and retain complete logs, exact revisions,
commands, and artifact identities. The successful statements print their axiom
lists for review.

The retained Valid declarations depend on `propext`,
`Classical.choice`, `Quot.sound`, and `Blaster.Tactic.blasterProven`. Blaster reports
SMT verification without a Lean proof term. The pure module build also replayed
an existing upstream CEK `sorry` warning. These observations retain the Lean,
ledger-model, CEK, and Blaster/SMT trust boundary; this candidate adds no admitted
proofs or replacement axioms.

## Limits and checkpoint 2

The symbolic fields vary only within the fixed Claim/Cancel shapes. The original
statements do not bind the symbolic `script` field to the evaluated program's
hash. Model validity and bounded execution do not establish deployed-ledger
reachability or validator-wide safety. The concrete controls use actual recorded
script hashes but retain the model's other limits.

Broader datum replacement and the intended meaning of the general rule remain
under [issue #35](https://github.com/no-witness-labs/contracts-library/issues/35).
App integration is deferred to checkpoint 2 under
[issue #96](https://github.com/no-witness-labs/contracts-library/issues/96).
Broader transaction-model coverage remains under
[issue #89](https://github.com/no-witness-labs/contracts-library/issues/89).
These standalone checks do not complete those broader requirements.
