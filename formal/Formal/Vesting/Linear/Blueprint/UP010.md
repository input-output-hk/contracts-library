# UP-010 standalone double-satisfaction candidate

Current helper references use `Formal.Support`. Statements below about unchanged
fully qualified names describe the earlier extraction checkpoint; the later
support-folder cleanup updates those names while preserving definition bodies.


This candidate preserves the four statements in
[DoubleSatisfaction.lean](DoubleSatisfaction.lean) at `d983a090` for the fixed
linear-vesting Claim and Cancel models. For two separately model-valid, accepted
contexts of the same action, it checks a combined transaction. The four-way
disjunction permits either run to reject or either run to accept after redirecting
every output. Both actions also have a separate applicability obligation.

The owner retained this disjunction for checkpoint 1. Acceptance after this one
address-and-datum redirection does not establish general output independence.
The stronger unconditional rejection requirement in
[issue #31](https://github.com/no-witness-labs/contracts-library/issues/31) remains
checkpoint-2 work. A validator that always returns unit legitimately satisfies
the retained disjunction.

The definitions and transaction models come from Irfan's work in
[PR #44](https://github.com/no-witness-labs/contracts-library/pull/44) at `99a5734`.
[PR #59](https://github.com/no-witness-labs/contracts-library/pull/59) extracted
these obligations. This checkpoint preserves their formulas, models, and
1,000,000-step CEK bound.

## Exact construction and claim

Let `h = claim p` and `g = claim q`, or use `cancel` for both. The premises require
`h` and `g` to be separately model-valid and accepted by the same pinned program.
They need not be different contexts. The helpers in
[CandidateHelpers.lean](../../../Support/CandidateHelpers.lean) construct the two runs:

1. `addSpendOf h g r` copies only `g`'s resolved own input into `h` under reference
   `r`. It appends a redeemer entry for `r` and a new key-address output holding
   that input's entire value, with no datum or reference script. The key is
   `attackerKey`. It preserves every original output of `h`.
2. `asSpendOf (addSpendOf h g r) g r` uses that same combined transaction for the
   second run. It selects `r` as the spent input and takes `g`'s datum and redeemer.
   The construction does not import `g`'s other inputs, outputs, signatories, or
   validity range.
3. `redirectOutputs` independently transforms each run by replacing every output
   address with `keyAddr attackerKey` and removing every output datum. It keeps
   output values and reference scripts. This also redirects the appended output.

The combined first context must be model-valid; this includes a fresh, correctly
ordered `r`. The statement has no separate validity premise for the second run
or either redirected variant. It requires at least one of these outcomes:

| Run | Allowed outcome |
| --- | --- |
| First combined run | Explicit rejection within the bound |
| Second combined run | Explicit rejection within the bound |
| Redirected first run | Unit-returning acceptance within the bound |
| Redirected second run | Unit-returning acceptance within the bound |

The applicability statements require valid accepted baselines and a valid
combined first context. They do not require either combined run to accept.
`rejects` means a CEK error or a non-unit halt within the bound. Exhausting fuel
establishes neither rejection nor acceptance. CEK steps are not a ledger CPU or
memory budget.

## Prepare and run

Run from `formal/`. Preparation requires no Aiken build or generated control
blueprint. [SourceCheck.lean](../../../../tests/UP010/SourceCheck.lean) compares the
tracked [control.json](../../../../tests/UP010/Inputs/control.json) bytes and decoded
program with the embedded Lean fixture. It also compares the decoded tracked
vesting artifact with the actual proof program. Both checks validate compiler
versions, V3, handler entries, and the absence of unapplied parameters.

```sh
lake build Formal.Support.CandidateHelpers Formal.Vesting.Linear.Blueprint.Types Formal.Vesting.Linear.Blueprint.Tx
mkdir -p .lake/build/lib/lean/tests/UP010
lake env lean --threads=4 -o .lake/build/lib/lean/tests/UP010/OutputDependentFixture.olean tests/UP010/OutputDependentFixture.lean
lake env lean --threads=4 tests/UP010/SourceCheck.lean
timeout --kill-after=5s 300s lake env lean --threads=4 Formal/Vesting/Linear/Blueprint/DoubleSatisfaction.lean
```

The main file expects four `Valid` observations and exit 0, in order:
`doubleSatisfaction_claim`, `doubleSatisfaction_claim_applies`,
`doubleSatisfaction_cancel`, and `doubleSatisfaction_cancel_applies`.
Run source files directly for fresh observations. All proof files use sequential
declaration checking and four Lean workers. A timeout is inconclusive. Blaster's
SMT verification and existing dependency trust remain part of these results.

## Controls

[OutputDependentControl.lean](../../../../tests/UP010/OutputDependentControl.lean)
uses a synthetic compiled Aiken V3 validator that requires at least one output
whose payment credential is a script. The source is
[output_dependent.ak](../../../../tests/UP010/Project/validators/output_dependent.ak).
Its 167-byte fixture has declared script hash
`c988dd668151710cdb060a1509185ab5301a7ec151a7373dcbc00b2d` and compiled-code SHA-256
`d845e54cb0be6203b5fd52c3e37d043f7cc41564502197fa98e3842932de9a75`.

Claim retains a script continuation in both baselines and both combined runs.
Both redirections remove all script payment credentials, making the retained
Claim implication false with applicable premises. The separate witness requires
both combined runs to accept and both redirected runs to reject, in addition to
the applicability premises. Cancel has no script output in its baseline and is
inapplicable to this control, so this negative control covers Claim only.

[AcceptingControl.lean](../../../../tests/UP010/AcceptingControl.lean) uses the
explicit synthetic UPLC program `λctx. unit`. Both actions must satisfy the main
disjunction through its acceptance alternatives, and both applicability checks
must pass. This positive control exercises those alternatives. Neither synthetic
control represents a deployed validator.

Both control files retain the original action models, argument encoding,
validity premises, transformations, acceptance/rejection semantics, and fuel.
The files sit outside the `Formal` library.

```sh
timeout --kill-after=5s 300s lake env lean --threads=4 tests/UP010/OutputDependentControl.lean
timeout --kill-after=5s 300s lake env lean --threads=4 tests/UP010/AcceptingControl.lean
```

Expected observations, in declaration order:

| File | Main Claim | Claim applicability | Further observations | Exit |
| --- | --- | --- | --- | --- |
| `OutputDependentControl.lean` | `Falsified` | `Valid` | Explicit Claim witness: `Valid` | 1 |
| `AcceptingControl.lean` | `Valid` | `Valid` | Main Cancel: `Valid`; Cancel applicability: `Valid` | 0 |

The negative control's expected failure counts only when all three observations
match. Import, elaboration, solver errors, or timeouts do not establish the control
outcome.

inputs and one output. Combining contexts adds one input and one output to each.

program; model validity does not establish full ledger or deployment reachability.
