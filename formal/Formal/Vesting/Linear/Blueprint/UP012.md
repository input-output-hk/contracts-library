# UP-012 standalone signer-removal candidate

This candidate checks the fixed linear-vesting Claim and Cancel models. Each model
has one signer. If a modeled context is valid and accepted, and removing its signer
preserves validity, the changed context must explicitly reject within 1,000,000
CEK steps. Separate applicability obligations require a witness to these premises.
Exhausting the CEK bound does not establish rejection.

The original definitions and transaction shapes come from Irfan's work in
[PR #44](https://github.com/no-witness-labs/contracts-library/pull/44) at `99a5734`,
extracted into [PR #55](https://github.com/no-witness-labs/contracts-library/pull/55).
[DropSigner.lean](DropSigner.lean) retains all four statements; [Tx.lean](Tx.lean)
owns the fixed models. [Types.lean](Types.lean) embeds the exact compiled program
from the tracked `onchain/plutus.json`, built with Aiken `v1.1.22+39d6b04`.
Its script hash is `95da21788eb1f59f51aad9669eb8c8b7081ab618c1f29b871925894a`.
Running these checks needs no generated CBOR file or Aiken rebuild.

## Run the candidate

Use Lean 4.24.0, Z3 4.15.2, and the committed Lake dependency pins. From `formal/`,
build the supporting modules, then run the four checks with a five-minute wall
clock limit. The source checks the declarations sequentially with four Lean workers.

```sh
lake build Formal.Vesting.Linear.Blueprint.Types Formal.Vesting.Linear.Blueprint.Tx
timeout --kill-after=5s 300s lake env lean --threads=4 --json Formal/Vesting/Linear/Blueprint/DropSigner.lean
```

Expected: four `Valid` results and exit 0, covering Claim rejection/applicability
and Cancel rejection/applicability. A timeout leaves the result unresolved.
Blaster uses SMT verification through `blasterProven`; these checks retain the
existing dependency trust assumptions and do not add admitted proofs.

Recorded standalone validation on 2026-11-02 used the Lean sources committed as
[`85b6b274df440b4f56d6c26d2285c84d0aac5429`](https://github.com/no-witness-labs/contracts-library/commit/85b6b274df440b4f56d6c26d2285c84d0aac5429).
Both removal properties and both applicability obligations returned `Valid` in
59.699 seconds, exit 0. The retained-signer controls below returned two `Falsified`
observations with counterexamples in 49.165 seconds, expected exit 1. The proof,
control, model, artifact, and dependency files remain unchanged by this documentation
update; these are the recorded results, not a new solver run. The final combined
source/build check remains a separate delivery gate.

The four original theorem axiom listings contain `propext`, `Classical.choice`,
`Quot.sound`, and `Blaster.Tactic.blasterProven`, without `sorryAx`.

## Run the negative control

[RetainedSigner.lean](../../../Properties/Universal/UP012/Tests/Standalone/RetainedSigner.lean) independently
states two deliberately false claims: require rejection while keeping the original
signer. It keeps the same program, models, premises, and CEK bound. This distinguishes
the actual signer-removal behavior from rejection of every modeled transaction.

```sh
timeout --kill-after=5s 300s lake env lean --threads=4 --json Formal/Properties/Universal/UP012/Tests/Standalone/RetainedSigner.lean
```

Expected: `Falsified` for both `retainedSigner_claim_control` and
`retainedSigner_cancel_control`, with counterexamples and a nonzero Lean exit.
That deliberate verification failure is the successful control outcome. An import,
compilation, or solver error, or a timeout, is not a successful control. The file
is outside the `Formal` library so routine library builds do not include it.

## Scope and later work

Claim uses two inputs and two outputs; Cancel uses two inputs and one output.
Both use one vested asset under fixed `policyA`, key credentials, and one signer.
The example assumes that signer is the intended required signer, with no extras.
This is a descriptive assumption, not an additional Lean premise or owner inference.

The checks establish dependence on removing the sole signer within these models;
they do not establish correct-owner authorization, arbitrary transaction coverage,
or ledger reachability. Required-signer semantics, additional signers, other
authorization policies, and broader model coverage remain checkpoint-2 work under
[issue #33](https://github.com/no-witness-labs/contracts-library/issues/33).
App integration and reconciliation with the native property/model banks belong
to checkpoint 2 under [issue #96](https://github.com/no-witness-labs/contracts-library/issues/96).
