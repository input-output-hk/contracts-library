# UP-015: bounded output-order example

This standalone candidate checks the pinned linear-vesting validator with the
Claim and Cancel transaction models in [Tx.lean](Tx.lean). Its compiled program
is embedded in [Types.lean](Types.lean); running these checks requires no generated
CBOR file, Python, or Nix.

[OutputOrder.lean](OutputOrder.lean) preserves the eight declarations extracted
from Irfan's work in PR #44 and recorded in PR #62. The primary checks require
acceptance after reordering outputs when the original context is model-valid
and accepted, and the reordered context remains model-valid. Acceptance uses
1,000,000 CEK steps, not a ledger CPU or memory budget.

## What the eight declarations cover

Each row below has a primary declaration and an `_applies` declaration.

| Declaration pair | Model transformation | Coverage |
| --- | --- | --- |
| `reverseOutputs_claim` | Reverse `[continuation, payout]`. | Swap the two Claim outputs. |
| `rotateOutputs_claim` | Move the first of those two outputs to the end. | The same Claim swap, not additional permutation coverage. |
| `reverseOutputs_cancel` | Reverse the singleton `[back]`. | Identity transformation; no reordering coverage. |
| `rotateOutputs_cancel` | Move the sole output to the end. | Identity transformation; no reordering coverage. |

The four historical applicability formulas require an accepted model-valid
original and a model-valid transformed context. They do not require a changed
output list. A passing Cancel applicability check therefore does not establish
a nontrivial reorder.

Two additional controls live outside the default `Formal` library:

- [NontrivialApplicability.lean](../../../../tests/UP015/NontrivialApplicability.lean)
  requires a valid accepted Claim whose valid reversal changes its output list.
  This stronger control supplements the historical applicability declarations.
- [RejectionControl.lean](../../../../tests/UP015/RejectionControl.lean)
  deliberately demands explicit rejection after the same Claim swap. It keeps
  the program, model, validity premises, and execution bound. Its expected result
  is Falsified, with a counterexample and a nonzero Lean exit status.

## Run the standalone checks

Use the repository's pinned Lean dependencies and Z3 environment. From `formal/`,
build the supporting modules, then run each proof command separately with a
five-minute wall-clock limit. Direct Lean invocations execute the checks afresh.

```sh
lake build Formal.Vesting.Linear.Blueprint.Types Formal.Vesting.Linear.Blueprint.Tx
timeout --kill-after=5s 300s lake env lean --threads=4 Formal/Vesting/Linear/Blueprint/OutputOrder.lean
timeout --kill-after=5s 300s lake env lean --threads=4 tests/UP015/NontrivialApplicability.lean
timeout --kill-after=5s 300s lake env lean --threads=4 tests/UP015/RejectionControl.lean
```

Expected observations:

| Command | Expected result |
| --- | --- |
| `OutputOrder.lean` | Eight Valid observations and successful compilation. |
| `NontrivialApplicability.lean` | One Valid observation and successful compilation. |
| `RejectionControl.lean` | One Falsified observation with a counterexample; compilation fails intentionally. |

Standalone validation on 2026-11-02 produced eight Valid observations in
141.322 seconds, the nontrivial applicability Valid in 20.673 seconds, and the
intended Falsified control with a counterexample in 37.115 seconds. The eight
original theorem axiom listings contain standard Lean axioms and `blasterProven`,
without `sorryAx`. A timeout, missing dependency, or unrelated compiler error
does not satisfy the rejection control.
Keep the complete logs and run each check under the agreed wall-clock budget.
The wall-clock budget is separate from the fixed CEK bound.

## Limits and checkpoint 2

Claim has two inputs, two outputs, one signer, and one vested asset under fixed
`policyA`. Cancel has two inputs and one output. Symbolic fields vary within
those shapes; the checks do not cover arbitrary transaction geometry. Model
validity does not establish deployed-ledger reachability. Successful Blaster
results retain its SMT trust boundary.

Broader output counts and permutations, useful Cancel reorderings, other models
and validators, and optimization remain under [issue #36](https://github.com/no-witness-labs/contracts-library/issues/36).
Output-index-sensitive validators may correctly reject a reorder unless the
corresponding redeemer indices also change. The present check is a scoped
output-order example, not a universal security requirement. New claim/model
choices and index handling need a separate decision.
App integration and reconciliation with native property/model banks belong to
checkpoint 2 under [issue #96](https://github.com/no-witness-labs/contracts-library/issues/96).
