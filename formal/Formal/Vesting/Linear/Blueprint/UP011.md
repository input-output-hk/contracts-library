# UP-011 standalone continuation payment-credential candidate

UP-011 checks a guarded mutation in the fixed linear-vesting Claim and Cancel
models. Given a model-valid, accepted context that rejects after its continuations
are redirected, replacing the first continuation's payment credential with a
different credential must explicitly reject. The changed context must also remain
model-valid. Acceptance and rejection use a bound of 1,000,000 CEK steps; this is
not a ledger execution budget, and exhaustion does not establish rejection.

[ContinuationElsewhere.lean](ContinuationElsewhere.lean) preserves all four formulas
from Irfan's [PR #44](https://github.com/no-witness-labs/contracts-library/pull/44)
at `99a5734f0e036b6abfb4c3f121a298e35fa2eff6`, extracted into
[PR #60](https://github.com/no-witness-labs/contracts-library/pull/60) at
`63c8ecce21de8897c252b6563ac90b2ccba343ed`.
They are now `Prop` definitions. [Checks.lean](../../../../tests/UP011/Checks.lean)
observes them with `#blaster`, including the expected false Cancel applicability
statement. It does not declare that statement as a proved theorem.

## Artifact and model

[Types.lean](Types.lean) embeds the compiled program from the tracked
`onchain/plutus.json` fixture, built with Aiken `v1.1.22+39d6b04`. Its Plutus V3
script hash is `95da21788eb1f59f51aad9669eb8c8b7081ab618c1f29b871925894a`.
The main checks need no external CBOR file or Aiken rebuild.

[Tx.lean](Tx.lean) keeps the original symbolic leaves and transaction shapes.
Claim has two inputs, a script continuation with an inline datum as its first
output, and a payout as its second output. Cancel has two inputs and a single key
output, with no continuation. Both use one signer, one vested asset under fixed
`policyA`, key credentials for the beneficiary and locker, and no staking credential
on their constructed addresses. The script credential remains a symbolic model
leaf. These models do not establish arbitrary transaction coverage or ledger
reachability.

## Run the candidate

Use Lean 4.24.0, Z3 4.15.2, and the committed `lake-manifest.json` pins:

| Dependency | Revision |
| --- | --- |
| Blaster | `402f6d22c1fc42e6e26255faac77e15b2450e4ab` |
| PlutusCore | `4ef48606303c45225d3ed2e2a87fc50280a763b7` |
| CardanoLedgerApi | `577e3eb03b5be09354cfdb1c0d0c12e9e16541a0` |

From `formal/`, prepare the definitions, then run the checks sequentially with
four Lean workers and a five-minute wall clock limit:

```sh
lake build Formal.Vesting.Linear.Blueprint.ContinuationElsewhere
timeout --kill-after=5s 300s lake env lean --threads=4 tests/UP011/Checks.lean
```

| Observation | Expected result | Meaning |
| --- | --- | --- |
| Claim property | `Valid` | The guarded payment-credential mutation rejects. |
| Claim applicability | `Valid` | Some accepted model-valid Claim meets every guard. |
| Cancel property | `Valid` | The implication holds without an applicable case. |
| Cancel applicability | `Falsified` | This Cancel model supplies no mutation coverage. |

The command expects the Cancel falsification explicitly, so the complete expected
sequence exits 0. Both command files enable `warningAsError`, which makes Blaster's
`Undetermined` warning fail the command. Any unexpected result, import failure,
or solver error also fails the check; a timeout leaves it unresolved and does not
satisfy the gate. A successful module build alone does not
establish any of these observations. The checks retain existing Blaster/SMT and
dependency trust assumptions; they add no axioms or admitted proofs.

## Run the applicable negative control

[ignore_address.ak](../../../../tests/UP011/Project/validators/ignore_address.ak)
is a deliberately faulty, unparameterized Plutus V3 spending validator. It requires
an inline datum on the first output and ignores that output's address. This accepts
the Claim baseline and its payment-credential mutation, because both retain that
datum. It rejects `redirectContinuations`, which changes every matching output to
the attacker key address **and removes its datum**. This control therefore exercises
the continuation-reliance guard while overlooking the credential mutation.

[Fixture.lean](../../../../tests/UP011/Fixture.lean) freezes the actual 132-byte
single-CBOR program built with Aiken `v1.1.21+42babe5` and stdlib `v3.0.0`.
Its script hash is `7d046e6d518c52d03749ee90e7284e38833ac98631f453d997b4a3d8`.
Its source check compares the authored source, manifest, dependency lock, compiler,
version, handlers, parameters, compiled bytes, and decoded program with the frozen
fixture and tracked [control.json](../../../../tests/UP011/Inputs/control.json).
The project ignores build output and retains the tested blueprint as a test input.

From `formal/`, compile and check the fixture, then run the negative control.
These commands use tracked inputs and need no Aiken rebuild:

```sh
mkdir -p .lake/build/lib/lean/tests/UP011
lake env lean -o .lake/build/lib/lean/tests/UP011/Fixture.olean tests/UP011/Fixture.lean
lake env lean tests/UP011/CheckArtifact.lean
timeout --kill-after=5s 300s lake env lean --threads=4 tests/UP011/NegativeControl.lean
```

[NegativeControl.lean](../../../../tests/UP011/NegativeControl.lean) keeps the exact
Claim property and applicability formulas, model, mutation, and bound, changing
only the executed validator. Expected: `Falsified` for the property and `Valid`
for applicability, with exit 0 because the falsification is intentional. This
distinguishes rejection of a changed credential from rejection caused by losing
the datum. The existing vesting Claim supplies the positive control. Both command
files live outside the default `Formal` library.

To reproduce the control with Aiken `v1.1.21+42babe5` and stdlib `v3.0.0`, rebuild
the source and compare the complete generated blueprint with the tracked input:

```sh
(cd tests/UP011/Project && aiken fmt --check && aiken build)
lake env lean tests/UP011/CheckRebuild.lean
```

This optional comparison fails if the rebuilt blueprint differs. Normal proof
execution reads the tracked test input, never the ignored build output.

## Scope and checkpoint 2

The mutation changes only the first continuation's payment credential and leaves
its staking credential, value, and datum unchanged. Its explicit inequality guard
excludes an identity mutation when a continuation exists. The continuation-reliance
guard requires rejection after a combined address-and-datum change; it does not
independently prove that the validator depends on the address. Cancel's redirect
is identity, so its accepted baseline cannot also reject after redirection.

These four statements establish neither the full address rule nor arbitrary
output-order coverage. Broader address protection and additional models remain
checkpoint-2 work under [issue #32](https://github.com/no-witness-labs/contracts-library/issues/32).
App integration and reconciliation with the current native property/model banks
remain checkpoint-2 work under [issue #96](https://github.com/no-witness-labs/contracts-library/issues/96).
