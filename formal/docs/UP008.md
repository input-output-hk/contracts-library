## Exact mutation and bounds

`addJunkFrom h r a` appends a new input at `unrelatedKey`. That input holds `a`
lovelace and one unit of the asset whose policy and name are both the bytes of
`"zzzzjunk"`. The mutation appends that asset to the first output whose payment
credential matches the spent input's payment credential. It sends the `a`
lovelace to a newly appended output at `unrelatedKey`.

The quantified integer `a` is **added lovelace**, not a token quantity or count.
The junk quantity is always `1`; the policy and name are fixed. The quantified
`r` identifies the appended input. The changed-context validity guard remains
responsible for admissible references, values, and transaction bookkeeping.
See [`CandidateHelpers.lean:82-101`](../Formal/Support/CandidateHelpers.lean#L82-L101).

Claim has two original inputs and two original outputs: a script continuation
followed by a key payout. Its vested policy is fixed to `"policyA"`; the asset
name, amounts, timestamps, credentials, and other leaves remain symbolic.
Cancel has two original inputs and one key output, with no continuation.
See `Formal/Vesting/Linear/Blueprint/Tx.lean:16-103`.

Both original rejection statements retain all four guards: model-valid baseline,
baseline acceptance, explicit rejection after redirecting continuations, and
model-valid mutation. Applicability asks for a witness satisfying those same
guards. Acceptance and rejection retain the **1,000,000 CEK-step** bound.
Rejection means an error or a non-unit halt within that bound; exhaustion is not
rejection. These are fixed transaction shapes checked against the repository's
ledger model, not arbitrary transactions or a deployed-ledger result.
See `Formal/Vesting/Linear/Blueprint/JunkToken.lean:18-53` and
`Formal/Support/Execution.lean:13-29`.

## Programs and controls

The original program is the unparameterized Plutus V3
`linear_vesting.linear_vesting.spend` entry in tracked `onchain/plutus.json`,
recorded with Aiken `v1.1.22+39d6b04` and script hash
`95da21788eb1f59f51aad9669eb8c8b7081ab618c1f29b871925894a`.
`Types.lean` embeds its compiled program. `Artifacts.lean` decodes the tracked
blueprint and checks that it equals the embedded program before running proofs.

The enforcing control is an actual Aiken V3 spending validator in
`Formal/Properties/Universal/UP008/Tests/Standalone/Project/validators/enforcing.ak`. It resolves its spent input, requires
the first output to carry the same script payment credential, and requires the
quantity of exactly `"zzzzjunk" / "zzzzjunk"` in that output to equal zero.
Redirection therefore fails the continuation check. The original Claim's
`"policyA"` differs from the junk policy, so the exact junk quantity is zero even
when the symbolic vested name equals `"zzzzjunk"` or `kept = 0`. The mutation adds
one unit of that exact asset. This control checks the asset quantity, not the
number of token entries.

The enforcing statements reuse the complete original Claim model, mutation,
guards, and fuel. Only the evaluated program changes. In particular, they leave
the model's script credential symbolic. See
`Formal/Properties/Universal/UP008/Tests/Standalone/EnforcingControl.lean:32-51` and
`Formal/Properties/Universal/UP008/Tests/Standalone/Project/validators/enforcing.ak:13-22`.

The enforcing program was compiled with Aiken `v1.1.21+42babe5`, stdlib `v3.0.0`,
and no parameters. Its 487 CBOR-encoded bytes are embedded in
`EnforcingControl.lean`; its script hash is
`e21ca2707f829187d132ebade676ffabe0bcb43cb191625ee4143e5f`.

`Inputs/control.json` freezes the tested blueprint as a tracked input.
`Project/provenance.json` records source, configuration, lockfile, compiled-code,
and frozen-blueprint SHA-256 digests. `Artifacts.lean` checks the source digests
and frozen blueprint against the embedded control. Normal standalone checks need
no generated Aiken output. `VerifyRebuild.lean` separately checks an optional
source rebuild. Generated `Project/build/` and `Project/plutus.json` are ignored.

## Reproduce

Use Lean `v4.24.0`, Z3 `4.15.2`, and the committed
`lake-manifest.json`: Blaster `402f6d22c1fc42e6e26255faac77e15b2450e4ab`,
PlutusCore `4ef48606303c45225d3ed2e2a87fc50280a763b7`, and CardanoLedgerApi
`577e3eb03b5be09354cfdb1c0d0c12e9e16541a0`. Keep dependency pins unchanged.

```sh

lake env lean Formal/Properties/Universal/UP008/Tests/Standalone/VerifyArtifacts.lean
```

Those commands perform no Blaster check. Then run the six proof attempts with
four Lean workers and sequential elaboration:

```sh
timeout 300s lake env lean --threads=4 --json Formal/Properties/Universal/UP008/Tests/Standalone/Checks.lean
```

The deadline is 300 seconds for the complete file, not for each theorem. Keep the
complete output and exit status, and match each observation to the table.
A timeout is inconclusive and does not authorize a longer retry. The four expected
Valid theorems print their axioms;
inspect those listings for unexpected admissions. Blaster's existing solver axiom
and the pinned dependencies remain trust assumptions. This work adds no `sorry`
or axiom. The inherited PlutusCore build emits an existing `sorry` warning in
`CekMachine.lean`; a successful dependency build does not remove that trust limit.
