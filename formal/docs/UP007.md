# UP-007 standalone continuation stake candidate

Current helper references use `Formal.Support`. Statements below about unchanged
fully qualified names describe the earlier extraction checkpoint; the later
support-folder cleanup updates those names while preserving definition bodies.


UP-007 checks whether changing the first continuation's staking credential causes
explicit rejection in the fixed linear-vesting Claim and Cancel models. The
expected Claim pair is `Falsified` rejection and `Valid` applicability. The expected
Cancel pair is `Valid` rejection and `Falsified` applicability, so Cancel provides
no applicable coverage.

The four original propositions from Irfan's work in
[PR #44](https://github.com/no-witness-labs/contracts-library/pull/44), extracted in
[PR #57](https://github.com/no-witness-labs/contracts-library/pull/57), remain in
[ContinuationStake.lean](../Formal/Vesting/Linear/Blueprint/ContinuationStake.lean).
They are proposition definitions, not asserted theorems. The six solver invocations
live in [Checks.lean](../tests/UP007/Checks.lean), outside the default `Formal`
library, because two expected results are `Falsified`.

Shared mutation helpers live in
[CandidateHelpers.lean](../Formal/Support/CandidateHelpers.lean), under their
shared `Formal.Support` namespace. The helper relocation preserves
their definition bodies; it does not change the four propositions.

## Claim and bounds

Every rejection obligation preserves the original premises. The baseline context
is valid and accepted; redirecting its continuations to a key address rejects.
The replacement staking credential differs from that of the first continuation,
and the mutated context is valid. The conclusion requires explicit rejection
within 1,000,000 CEK steps. Exhaustion of that bound does not establish rejection.
Each applicability obligation asks for a witness satisfying those same premises.

[Tx.lean](../Formal/Vesting/Linear/Blueprint/Tx.lean) fixes Claim to two inputs and
two outputs, with the continuation first. Cancel has two inputs and one key output.
Both models use one vested asset under the fixed `policyA`, key credentials for
the beneficiary and locker, and one signer. The own script credential remains
symbolic. The original own input and continuation both have no staking credential.
The mutation affects only the first matching continuation. These results establish
no arbitrary output order, multiple-continuation, or full ledger coverage.

## Programs and control

[Types.lean](../Formal/Vesting/Linear/Blueprint/Types.lean) embeds the exact
linear-vesting bytes from the tracked `onchain/plutus.json`, compiled with Aiken
`v1.1.22+39d6b04`. The recorded script hash is
`95da21788eb1f59f51aad9669eb8c8b7081ab618c1f29b871925894a`.
The original candidate does not require rebuilding Aiken or generating a CBOR file.

The synthetic enforcing control has retained
[Aiken source](../tests/UP007/Project/validators/stake_control.ak), manifest, and
lock file. It resolves the own input from the spending reference and requires the
first output to have the same payment credential and staking credential. Its
opaque datum and redeemer accept the original model's data encodings. Claim's
first output is its continuation; redirecting it breaks payment-credential
equality, and changing its staking credential breaks stake equality.

[Control.lean](../tests/UP007/Control.lean) freezes the compiled V3 program and
repeats the original Claim propositions with only the executed program replaced.
It keeps the model, validity guards, continuation-reliance guard, and CEK bound.
The authored validator exists only as a test control. Its script hash is `d94e30a6868bb280eba4c6479283a5cfd60f78d40698410ed383a590`.
[Inputs/control.json](../tests/UP007/Inputs/control.json) retains the exact
blueprint used for the fixture. [artifact.json](../tests/UP007/artifact.json) records
its compiler, source hashes, blueprint hash, and compiled-byte hash. The applicable
original Claim falsification supplies the negative counterpart to this enforcing
control.

## Reproduce

Use Lean 4.24.0, Z3 4.15.2, and the committed Lake manifest. The dependency commits
remain unchanged:

| Dependency | Commit |
| --- | --- |
| Blaster | `402f6d22c1fc42e6e26255faac77e15b2450e4ab` |
| PlutusCore | `4ef48606303c45225d3ed2e2a87fc50280a763b7` |
| CardanoLedgerApi | `577e3eb03b5be09354cfdb1c0d0c12e9e16541a0` |

From `formal/`, type-check the proposition definitions and frozen control without
running the solver:

```sh
lake build Blaster Formal.Vesting.Linear.Blueprint.ContinuationStake
mkdir -p .lake/build/lib/lean/tests/UP007
lake env lean -o .lake/build/lib/lean/tests/UP007/Control.olean tests/UP007/Control.lean
```

Verify the retained artifacts from `formal/`, using Bash, jq, xxd, and sha256sum:

```sh
bash tests/UP007/verify-artifacts.sh
```

The verifier checks retained source hashes, the frozen blueprint hash and compiler
version, the control's compiled bytes and recorded hashes, and equality between
the embedded original program and the tracked vesting blueprint. It requires no
Aiken installation or generated `Project/plutus.json`. The frozen Lean fixtures
are sufficient for solver execution.

Optionally rebuild the synthetic source with Aiken `v1.1.21+42babe5` and stdlib
`v3.0.0`, then compare the full rebuilt blueprint with the retained input:

```sh
(cd tests/UP007/Project && aiken fmt --check && aiken build)
cmp tests/UP007/Inputs/control.json tests/UP007/Project/plutus.json
```

Generated `Project/build/` and `Project/plutus.json` remain ignored. Rebuilding the
synthetic source is a separate provenance check.

Run all six obligations sequentially with four Lean workers and a five-minute
wall-clock limit:

```sh
timeout --kill-after=5s 300s lake env lean --threads=4 tests/UP007/Checks.lean
```

| Check | Recorded result | Interpretation |
| --- | --- | --- |
| Original Claim rejection | `Falsified` | A guarded valid stake mutation avoids explicit rejection. |
| Original Claim applicability | `Valid` | The Claim premises have a witness. |
| Original Cancel rejection | `Valid` | Read with the next result: no applicable coverage. |
| Original Cancel applicability | `Falsified` | The fixed Cancel model supplies no continuation-dependent witness. |
| Enforcing Claim rejection | `Valid` | The synthetic control rejects the guarded mutation. |
| Enforcing Claim applicability | `Valid` | The enforcing control supplies an applicable baseline. |

The retained six-check run produced four `Valid` and two `Falsified` observations
in 164.511 seconds, with exit 1 from the two expected failed theorem checks. An
import error, solver error, or timeout is not an expected falsification.

That solver run preceded the shared-helper relocation. A later module build
compiled `Properties`, `CandidateHelpers`, `Types`, `Tx`, and `ContinuationStake`
successfully; it did not rerun the six solver obligations. Source comparison
confirms that the four proposition bodies and transaction models match the
original extraction, while the helper bodies and fully qualified names survive
the move unchanged. The retained checks, control, inputs, and artifact verifier
also match the pause snapshot. This supports reuse of the recorded outcomes
through the relocation, without claiming a new solver run on the final commit.
The run receipt records elapsed time and exit status but no tested-source commit.

The retained blueprint identifies the synthetic artifact's compiler. Delivery
review confirmed the source and artifact hashes, but no retained raw Aiken build
log supports a separate build-execution claim here. The normal verification path
uses `Inputs/control.json` and does not depend on generated Aiken output. Final
combined-source compatibility checks remain a delivery gate.
Blaster uses the existing SMT trust path; dependency build warnings about existing
admitted declarations remain part of the trust boundary. No admitted proof is
added to these fixtures.

## Checkpoint 2

This guarded first-continuation mutation check does not establish
[issue #28](https://github.com/no-witness-labs/contracts-library/issues/28)'s full
input/output staking-credential preservation rule. Broader credential preservation,
other transaction models, and generalization remain checkpoint-2 work. App
integration and current native property/model bank adoption also belong to
checkpoint 2. This standalone candidate leaves those tasks open.
